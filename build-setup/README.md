# build-setup

Local, non-upstream setup for building and keeping current a **multi-gfx AMD
(ROCm) llama.cpp**. This folder holds the pieces that are *yours*, not part of
upstream llama.cpp. Everything here is version-controlled so the setup
survives and is reviewable.

There is exactly **one** upstream file touched: `app/llama.cpp` (the
`llama update` source-build check). Everything else in this folder is new.

## What this is for

A two-card ROCm box where the cards are on **different** gfx targets:

- RX 9060 XT    -> gfx1200 (gfx12.0.0)
- AI PRO R9700 -> gfx1201 (gfx12.0.1)

The goal is one `llama` binary that targets **both** gfx variants natively, so
no `HSA_OVERRIDE_GFX_VERSION` workaround is needed.

### Why a custom build

The `llama.app` installer (`curl -fsSL https://llama.app/install.sh | sh`)
downloads a **single-gfx-target** prebuilt: a probe picks one target and
fetches a binary compiled only for it. On a box with two RDNA4 cards on
*different* targets, the other card fails the HIP code-object load
(`hip_code_object.cpp: ...getStatFunc... Assertion 'err == hipSuccess'
failed`). A self-build that targets both cards fixes it.

The installer's whole footprint is `~/.llama-app/` (three files: `llama`,
`cuda-probe`, `rocm-probe`) plus a copy of `llama` into `~/.local/bin`. It
installs nothing else. Uninstall: `rm -rf ~/.llama-app`.

## Layout

```
llama.cpp/                       (this repo, a local fork)
├── app/llama.cpp                (ONLY upstream file modified: update check)
└── build-setup/                 (everything else, all yours)
     ├── README.md               (this file)
     └── llama-reinstall.sh      (wrapper/install helper, platform-agnostic)

~/.local/                        (runtime, generated, NOT in git)
├── bin/                         thin .sh wrappers (generated by llama-reinstall)
├── lib/llama/bin/               the real ELF binaries (from cmake --install)
└── lib/                         all shared libs (libggml-hip, libllama*, ...)
```

`~/.local/bin/llama-reinstall` is a **symlink** to
`build-setup/llama-reinstall.sh`, so the update flow is unchanged but the
script is versioned.

## The update flow (2 commands)

```
cmake --install build --prefix "$HOME/.local"
llama-reinstall
```

1. `cmake --install` lays the freshly-built ELFs and libs into `~/.local/`.
2. `llama-reinstall` moves the ELFs out of `~/.local/bin/` into
   `~/.local/lib/llama/bin/` and (re)generates a thin wrapper in
   `~/.local/bin/` for each one.

### Why the wrappers

The installed ELFs have **no RPATH** — CMake clears the runtime path at install
time (the "Set non-toolchain portion of runtime path ... to ''" lines). So
they cannot find the shared libs in `~/.local/lib` on their own, and
`~/.local/lib` is not a default library search path. Each wrapper just does:

```sh
export LD_LIBRARY_PATH="$HOME/.local/lib:$LD_LIBRARY_PATH"
export LLAMA_SRC_DIR="$HOME/Documents/code/llama.cpp"
exec "$HOME/.local/lib/llama/bin/<name>" "$@"
```

Wrapping the **whole suite** (not just `llama`) means `llama-server`,
`llama-bench`, etc. all work too. Because the wrappers live in `~/.local/bin`
while the real ELFs live in `~/.local/lib/llama/bin`, `cmake --install` can
never clobber the wrappers — it only touches the real ELFs, which
`llama-reinstall` then re-wraps. That is the whole point of the two-directory
split.

## The `llama update` feature

Upstream, `llama update` only works for `llama.app` builds
(`LLAMA_INSTALL_BUILD`) — a source build prints *"Updates are available only
when installed from https://llama.app"*.

The `app/llama.cpp` change repurposes the **source-build** branch: instead of
that message, it reports how the installed binary compares to the source tree
and to upstream, and prints the commands to catch up. It never auto-rebuilds
(manual, experimental setup). It:

- reads the **embedded** commit/build number (`llama_commit()` /
  `llama_build_number()` — already in every build via `build-info.h`)
- `git fetch origin master`, then compares three things:
  installed vs local `HEAD`, and local `HEAD` vs `origin/master`
- prints a clear status + the exact catch-up commands
- exits `0` when up to date, `2` when behind (scriptable)
- degrades gracefully if offline or the dir is not a git checkout

It finds the source dir via `LLAMA_SRC_DIR` (set by the wrapper). Example:

```
$ llama update
installed build : 51ce9c11a (build 11456)
local source     : 51ce9c11a
upstream master : 51ce9c11a

up to date.
```

When behind:

```
$ llama update
installed build : abeada335 (build 11455)
local source     : 310991409
upstream master : abeada335

-> the installed build is older than your local source.
    rebuild it:
      cmake --build build --config Release -j$(nproc)
      cmake --install build --prefix "$HOME/.local"
-> upstream is ahead of your local source. To update:
      git -C '...' fetch origin && git -C '...' pull
      cmake --build build --config Release -j$(nproc)
      cmake --install build --prefix "$HOME/.local"
```

## Building from scratch (fresh clone)

```
sudo pacman -S base-devel rocm-hip-sdk cmake git     # Manjaro
git clone https://github.com/ggml-org/llama.cpp && cd llama.cpp

cmake -B build \
     -DGGML_HIP=ON \
     -DCMAKE_HIP_ARCHITECTURES="gfx1200;gfx1201" \
     -DGGML_HIP_F16C=ON \
     -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release -j$(nproc)

# verify BOTH targets are in the HIP backend lib (not the llama launcher):
strings build/bin/libggml-hip.so.0.*.26.0 \
     | grep -oE 'amdgcn-amd-amdhsa--gfx[0-9]{3,4}' | sort | uniq -c

# install + wrap:
cmake --install build --prefix "$HOME/.local"
llama-reinstall
which llama && llama --version
```

### Flag notes

- `CMAKE_HIP_ARCHITECTURES` is the CMake-native target list (modern main).
  Older eras used `AMDGPU_TARGETS`; current master accepts both because
  `ggml/src/ggml-hip/CMakeLists.txt` forwards
  `AMDGPU_TARGETS` -> `GPU_TARGETS` -> `CMAKE_HIP_ARCHITECTURES`.
- `-DGGML_HIP_F16C=ON` — faster kernels (needs AVX2/FMA; present on x86_64).
- Build **HIP only**; leave CUDA off (it's off by default with no CUDA
  headers). Don't enable both.
- Use a **dedicated build dir** (`cmake -B build`). If you change targets,
  delete `build/` and reconfigure so a stale cache doesn't carry over.

### Size

Each gfx target adds ~60 MB of code objects to `libggml-hip.so` (measured:
gfx1200 alone ~79 MB, gfx1200+gfx1201 ~141 MB). That is the kernel code
itself, not bloat — the trade-off for a single binary that serves both cards.

## Maintenance / re-applying after a `git pull`

The `app/llama.cpp` change is a local, non-upstreamable tweak. On a
`git pull` it will conflict or be wiped. Keep this whole setup on a **local
branch** (e.g. `local/rocm-setup`) so `git pull` becomes a rebase you control:

```
git checkout -b local/rocm-setup      # once, to hold the changes
git add app/llama.cpp build-setup/
git commit -m "local: ROCm multi-gfx build setup + llama update check"

# later, to catch up with upstream:
git fetch origin
git rebase origin/master              # or: git merge origin/master
cmake --build build --config Release -j$(nproc)
cmake --install build --prefix "$HOME/.local"
llama-reinstall
```

If a rebase conflicts in `app/llama.cpp`, the hunk is small (one function);
re-apply it by hand or from a saved patch.
