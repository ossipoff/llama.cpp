# build-setup

Local, non-upstream setup for building and keeping current a **multi-gfx AMD
(ROCm) llama.cpp**. This folder holds the pieces that are *yours*, not part of
upstream llama.cpp. Everything here is version-controlled so the setup
survives and is reviewable.

There is exactly **one** upstream file touched: `app/llama.cpp` (the
`llama update` command, repurposed for source builds). Everything else in
this folder is new.

## What this is for

A two-card ROCm box where the cards are on **different** gfx targets:

- RX 9060 XT     -> gfx1200 (gfx12.0.0)
- AI PRO R9700 -> gfx1201 (gfx12.0.1)

The goal is one `llama` binary that targets **both** gfx variants natively, so
no `HSA_OVERRIDE_GFX_VERSION` workaround is needed.

### Why a custom build

The `llama.app` installer (`curl -fsSL https://llama.app/install.sh | sh`)
downloads a **single-gfx-target** prebuilt: a probe picks one target and
fetches a binary compiled only for it. On a box with two RDNA4 cards on
*different* targets, the other card fails the HIP code-object load
(`hip_code_object.cpp: ...getStatFunc... Assertion 'err == hipSuccess'
failed`). A self-build that targets both cards fixes it.

The installer's whole footprint is `~/.llama-app/` (three files: `llama`,
`cuda-probe`, `rocm-probe`) plus a copy of `llama` into `~/.local/bin`. It
installs nothing else. Uninstall: `rm -rf ~/.llama-app`.

## The one command: `llama update`

This is the daily driver. Upstream, `llama update` only works for
`llama.app` builds (`LLAMA_INSTALL_BUILD`) — a source build prints *"Updates
are available only when installed from https://llama.app"*. The `app/llama.cpp`
change repurposes the **source-build** branch into a full, prompt-gated
catch-up:

```
$ llama update
installed build : 4097fc47f (build 11460)
local source      : 4097fc47f
upstream master   : 5ad1c5da0

up to date.
```

When it detects drift, it tells you what it would do and asks:

```
$ llama update
installed build : ...
local source      : ...
upstream master   : ...

-> the installed build is older than your local source.
-> upstream is ahead of your local source.

This will: rebase onto upstream, rebuild, reinstall, and re-wrap.
Update now? [Y/n]
```

Answer **Y** (or just Enter) and it runs the whole catch-up inline:

```
    Rebasing onto origin/master ...
    Building (the slow step) ...
    Installing + re-wrapping ...
    Done. Updated to: <new-commit>
```

Answer **n** (or run it non-interactively) and it does **no work** — it just
prints the manual commands and exits 2.

### How it decides "drift"

- **Installed vs. local source**: prefix compare of the **embedded** commit
   (`llama_commit()` / `llama_build_number()`, already baked into every build
   via `build-info.h`) against `HEAD` (7 chars). The installed commit may be
   longer than 7 chars, so it's a prefix match, not an equality test.
- **Local source vs. upstream**: because we carry local commits, "up to date"
   means `origin/master` is an **ancestor** of `HEAD` (`git merge-base
   --is-ancestor`), *not* that the hashes are equal — our local commit always
   changes the hash.
- It `git fetch origin master` first, and degrades gracefully if offline or
   the dir is not a git checkout.
- It finds the source dir via `LLAMA_SRC_DIR` (set by the wrapper).

### Exit codes (scriptable)

| Code | Meaning |
|---|---|
| 0 | up to date, or updated cleanly |
| 1 | stopped on a rebase conflict or build failure (tree left clean) |
| 2 | behind, but not updated (non-interactive, or you answered n) |

### Safe stops

It is "aggressive about doing the work, conservative about never silently
leaving you broken":

- **Rebase conflict** → `git rebase --abort` (tree left clean), prints how to
   resolve and resume, exits 1. Re-run `llama update` after resolving.
- **Build failure** → prints the log tail, exits 1. Re-run after fixing.
- It never re-does a rebase that's already complete (the ancestry check means
   "already on top of upstream" = skip straight to rebuild).

## Layout

```
llama.cpp/                        (this repo, a local fork)
├── app/llama.cpp                 (ONLY upstream file modified: the update command)
└── build-setup/                  (everything else, all yours)
      ├── README.md               (this file)
      └── llama-reinstall.sh      (wrapper/install helper, platform-agnostic)

~/.local/                         (runtime, generated, NOT in git)
├── bin/                          thin .sh wrappers (generated by llama-reinstall)
├── lib/llama/bin/                the real ELF binaries (from cmake --install)
└── lib/                          all shared libs (libggml-hip, libllama*, ...)
```

`~/.local/bin/llama-reinstall` is a **symlink** to
`build-setup/llama-reinstall.sh`, so it's versioned but lives on PATH.

### Why the wrappers (and the two-dir split)

The installed ELFs have **no RPATH** — CMake clears the runtime path at install
time (the "Set non-toolchain portion of runtime path ... to ''" lines). So
they cannot find the shared libs in `~/.local/lib` on their own, and
`~/.local/lib` is not a default library search path. Each wrapper just does:

```sh
export LD_LIBRARY_PATH="$HOME/.local/lib:$LD_LIBRARY_PATH"
export LLAMA_SRC_DIR="$HOME/Documents/code/llama.cpp"
exec "$HOME/.local/lib/llama/bin/<name>" "$@"
```

Wrapping the **whole suite** (not just `llama`) means `llama-server`,
`llama-bench`, etc. all work too. Because the wrappers live in `~/.local/bin`
while the real ELFs live in `~/.local/lib/llama/bin`, `cmake --install` can
never clobber the wrappers — it only touches the real ELFs, which
`llama-reinstall` then re-wraps. That is the whole point of the split.

`llama update` runs `llama-reinstall` at the end of its update flow, so you
rarely need to call it directly.

## The manual fallback (what `llama update` prints if you decline)

If you'd rather do it by hand — or after a rebase conflict you had to resolve
— the sequence is:

```
cd <source-dir> && git rebase origin/master
cmake --build build --config Release -j$(nproc)
cmake --install build --prefix "$HOME/.local"
llama-reinstall
```

## Building from scratch (fresh clone)

```
sudo pacman -S base-devel rocm-hip-sdk cmake git      # Manjaro
git clone https://github.com/ggml-org/llama.cpp && cd llama.cpp

cmake -B build \
      -DGGML_HIP=ON \
      -DCMAKE_HIP_ARCHITECTURES="gfx1200;gfx1201" \
      -DGGML_HIP_F16C=ON \
      -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release -j$(nproc)

# verify BOTH targets are in the HIP backend lib (not the llama launcher):
strings build/bin/libggml-hip.so.0.*.26.0 \
      | grep -oE 'amdgcn-amd-amdhsa--gfx[0-9]{3,4}' | sort | uniq -c

# install + wrap:
cmake --install build --prefix "$HOME/.local"
llama-reinstall
which llama && llama --version
```

### Flag notes

- `CMAKE_HIP_ARCHITECTURES` is the CMake-native target list (modern main).
   Older eras used `AMDGPU_TARGETS`; current master accepts both because
   `ggml/src/ggml-hip/CMakeLists.txt` forwards
   `AMDGPU_TARGETS` -> `GPU_TARGETS` -> `CMAKE_HIP_ARCHITECTURES`.
- `-DGGML_HIP_F16C=ON` — faster kernels (needs AVX2/FMA; present on x86_64).
- Build **HIP only**; leave CUDA off (it's off by default with no CUDA
   headers). Don't enable both.
- Use a **dedicated build dir** (`cmake -B build`). If you change targets,
   delete `build/` and reconfigure so a stale cache doesn't carry over.

### Size

Each gfx target adds ~60 MB of code objects to `libggml-hip.so` (measured:
gfx1200 alone ~79 MB, gfx1200+gfx1201 ~141 MB). That is the kernel code
itself, not bloat — the trade-off for a single binary that serves both cards.

## Maintenance / re-applying after a `git pull`

The `app/llama.cpp` change is a local, non-upstreamable tweak. Keep this whole
setup on a **local branch** (this one: `local/rocm-setup`) so a `git pull`
becomes a rebase you control, and `llama update` becomes the catch-up command:

```
# first time, to hold the changes (already done on this branch):
git checkout -b local/rocm-setup
git add app/llama.cpp build-setup/
git commit -m "local: ROCm multi-gfx build setup + llama update"

# later, to catch up with upstream: just run
llama update            # prompts, then rebases + rebuilds + reinstalls + rewraps
```

If `llama update` hits a rebase conflict in `app/llama.cpp` (it aborts and
leaves the tree clean), the hunk is small (one function); resolve it by hand
or from a saved patch, then re-run `llama update` to finish.
